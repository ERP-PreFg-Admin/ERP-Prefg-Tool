# Add Instamart, before handing out the extension

## Context

The extension is about to be shared with the team, so the platform list should be
complete first. The ask was Instamart, Blinkit and Myntra — but inspection shows only
one of the three is actually missing.

| | sheet rows | with links | parser | scraped today |
|---|---|---|---|---|
| **Blinkit** | 21 | 16 on `blinkit.com` | ✅ exists | ✅ 16/16 priced |
| **Myntra** | 75 | 75 on `www.myntra.com` | ✅ exists | ✅ 75/75 priced |
| **InstaMart** | 21 | **10 on `www.swiggy.com`** | ❌ none | ❌ tab never read |

So **Blinkit and Myntra need no code.** Their only gap is sheet data — 5 blinkit rows
have no product link. Instamart is genuinely absent: no parser, no host allowlist entry,
and `SHEET_TABS` in `.env` does not include the tab, so `load_rows()` never even opens it.

## What the probe found

Three live Instamart pages, fetched both ways:

- **HTTP: `202` with 0 bytes** — the same WAF-challenge pattern as zepto. **Browser
  required.**
- **Rendered: ~170KB, parses cleanly.** JSON-LD `Product.offers.price` appears **exactly
  once** per page: 403, 382, 449. Names matched their SKUs.
- `MCaf396_WB` read **382**, matching amazon/blinkit/myntra — a good cross-check that the
  right field is being read.
- Product id is in the URL: `/instamart/item/AMZGIBN2K9`.

**So the parser is nearly free.** Price comes from the existing shared `jsonld_price()`
helper with no changes; MRP falls back to the existing `mrp_near()`. That is exactly the
default path flipkart already uses.

Two genuine complications, both new:

1. **`"mrp"` is not reliably present.** One probe saw the key, a later one did not. So
   many Instamart rows will legitimately read "no MRP", and the sheet has no `mrp` column
   to fall back on. Expect patchy discount coverage rather than treating it as a bug.
2. **Instamart returns a price for out-of-stock items** — 2 of the 3 sampled were
   `OutOfStock` yet still quoted 403 and 449. Comparing an out-of-stock price against an
   agreed rate is misleading, so availability has to be captured rather than ignored.

## Changes

All small, and all in places that already have a slot for a new platform.

| file | change |
|---|---|
| `tracker/config.py` | `ALLOWED_HOSTS["instamart"] = {"swiggy.com", "www.swiggy.com"}`; add `"instamart"` to `QC_CHANNELS` — it is quick commerce, so prices are store-specific |
| `tracker/rules.json` | `channels.instamart = {price: ["@jsonld"], mrp: ["@mrp_near"]}` and `product_id.instamart = "/instamart/item/([A-Z0-9]{6,14})"` |
| `tracker/parsers.py` | `instamart()` — three lines, reusing `jsonld_price` + `mrp_near`; register in `PARSERS` |
| `.env` | `SHEET_TABS` gains `InstaMart` |
| `tracker/scrape.py` | record `availability` from the JSON-LD offer when present |
| `tracker/selfcheck.py` | fixtures: JSON-LD price, no-MRP case, out-of-stock case, and `product_key` for a swiggy URL |
| `extension/rules.json` | regenerated by `export-bau`, so `parse.js` gains Instamart with no JS change |
| `extension/fetcher.js` | add `instamart` to `NEEDS_TAB` (HTTP returns 202) |
| `extension/manifest.json` | `host_permissions` gains `https://www.swiggy.com/*` |

Because `parse.js` reads the shared `rules.json` and dispatches through the same registry,
the extension picks Instamart up from the config alone — no parser written twice.

## The one thing that does not carry over

**`store_ok` cannot use the existing marker for Instamart.** The rendered page contains a
list of serviceable cities — the probe matched "Mumbai", "Bengaluru" *and* "Delhi" on the
same page. So the current "does the page mention our city" test would return a **false
pass** and quietly assert the delivery area is correct when it may not be.

Options, to decide during implementation:
- find an Instamart-specific marker that only appears once an address is set, or
- leave `store_ok = None` for Instamart (unknown, not false) rather than assert something
  untrue

Recording an unverified `None` is the honest default; a false pass is the failure mode
this whole check exists to prevent.

## Verification

1. `python track.py selfcheck` green — it encodes the six parser bugs fixed this week.
2. New fixtures pass: JSON-LD price read, missing MRP yields `no MRP` not `0%`,
   out-of-stock recorded, `product_key("instamart", …)` → `instamart:amzgibn2k9`.
3. `python track.py verify 3` reaches Instamart rows and prints prices, with no
   `blocked URL` rejections.
4. Cross-check against known values: `MCaf396_WB` should read **382**, matching amazon,
   blinkit and myntra.
5. One scrape → `prices.csv` gains ~10 instamart rows; dashboard shows an INSTAMART
   column.
6. `export-bau` → `bau.json` gains instamart targets with keys; extension sweep loads them
   and routes them through a tab, not `fetch()`.
7. Confirm the HTTP worker path is never used for instamart — its `202` must not be
   parsed into a null price and reported as out of stock.

## Open items

- **Out-of-stock pricing.** Should an out-of-stock Instamart price count toward compliance?
  My inclination is to record it but exclude it from over-agreed until you say otherwise —
  it is not a price anyone can actually pay.
- **`store_ok` for Instamart** — needs a marker that proves the address resolved, or stays
  `None`.
- **Location cookies for Instamart** are not captured. It is quick commerce, so prices are
  store-specific; until the address is set in whichever browser runs it, Instamart prices
  are default-store like zepto's were.
